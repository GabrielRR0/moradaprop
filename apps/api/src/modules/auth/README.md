# auth
Registro, verificación de correo, login, sesiones, recuperación de contraseña, 2FA y Google.

**Estructura:** `controllers/` (rutas por acceso: `public/` y `private/user/`) -> `services/auth.service.ts` (fachada) -> services por tema (`registration/`, `sign-in/`, `password/`, `two-factor/`, `google/`, `account/`). `contracts/dto` valida cada entrada y `contracts/resources` describe cada respuesta. `guards/jwt-auth.guard.ts` es el guard global de token. Cada carpeta tiene su README.

**Cómo funciona:** el access token (JWT corto) viaja en el header; el refresh token es de un solo uso y rota en cada /refresh (web: cookie httpOnly; móvil: body). Se puede entrar con **passkey** (huella, Face ID, Windows Hello) sin correo ni clave (`controllers/public/passkey-login.controller.ts`; la verificación vive en `security/passkeys`), y la passkey también sirve de segundo paso cuando el inicio es muy raro. Las respuestas de login, refresh y verificación de correo traen `enrollment` (si la cuenta debe activar passkey o 2FA y hasta cuándo; ver `security/second-factor`). Cada inicio de sesión pasa por `security/access-risk` (país, red y dispositivo: ver su README); las sesiones quedan atadas a un dispositivo y solo se renuevan desde él. La rotación es atómica (varias peticiones con el mismo refresh: gana una, las demás reciben 401); reusar un refresh ya rotado hace más de 10 s cierra todas las sesiones, y dentro de esos 10 s solo se rechaza (dos pestañas legítimas no se expulsan). Los códigos de 6 dígitos se guardan hasheados, con intentos y cooldown. Las respuestas no revelan si un correo existe.

**Rutas:** /api/auth/*. **Tests:** test/e2e/auth-*.e2e-spec.ts.
